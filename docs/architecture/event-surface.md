# Event surface design: inbound webhooks and outbound transition events

Status: Proposed (design record, issue #313, C.4)
Owner: coordinator
Last updated: 2026-08-23

## Purpose

Cortxt does not yet own a generic event/webhook surface. Today the only
external triggers are human/git actions: the daemon polls, Atlas sync runs
on a schedule or manual dispatch, and the site deploys are manual Pages API
POSTs because no GitHub webhook exists (#305). ADR-024 chose MCP as the
external integration *form* and deferred event/callback delivery; ADR-029
lists "a webhook payload" as a future untrusted-input source. This document
defines one event surface that every candidate from #305 (C.1-C.3) and any
future consumer becomes an instance of.

This is a design record only. It does not change production code; a future
build issue implements the surface.

## Design goals

1. One envelope and one verification story for every inbound event, so
   C.1 (push), C.2 (issue/label), and C.3 (review event) share the same
   HMAC/replay/retry handling instead of three ad-hoc paths.
2. One outbound event format for run/claim/label transitions, so future
   consumers (CI, status dashboards, notifications) subscribe without
   owning dispatch internals.
3. Untrusted-input discipline per ADR-029: every inbound payload is
   validated against a closed schema before any effect, and never carries
   secrets, prompts, or model reasoning.

## Inbound events (Cortxt receives an event and reacts)

### Envelope

Every inbound event is wrapped in one envelope before any consumer logic:

```json
{
  "id": "evt_01J0...",              // unique, generated by the sender
  "type": "github.push",            // namespaced event type
  "occurred_at": "2026-08-23T12:00:00Z",
  "source": "github",
  "data": { }                       // closed-schema payload for the type
}
```

- `id` is the idempotency key. Consumers dedupe on it within a bounded
  window (below).
- `type` drives the closed schema the payload must validate against.
- Unknown types are rejected (fail closed), never silently ignored.

### Delivery mechanics

| Concern | Rule |
|---|---|
| Transport | HTTPS POST to a loopback-only listener on the operator machine, or a GitHub Actions workflow for GitHub-sourced events (C.1-C.3 use the workflow path; a local listener is the general case) |
| HMAC verification | `X-Hub-Signature-256` (GitHub) or an equivalent `X-Cortxt-Signature` for non-GitHub senders: `sha256=<hex>` of the raw body with the shared secret; compare constant-time (e.g. `hmac.compare_digest`); missing/mismatched signature is rejected before parsing |
| Secret | Per-source shared secret from the operator's credential broker (`cortxt credentials inject`), never in the repo, never logged |
| Replay protection | Idempotency window (recommended default 5 minutes, operator-tunable): an `id` already seen inside the window is a no-op; outside the window a replayed `id` is accepted only if the payload hash matches the stored one, else rejected |
| Retries | At-least-once with dedupe: senders may retry on 5xx; the idempotency key makes retries safe. Exactly-once is not attempted (no distributed transaction) |
| Failure behavior | Validation/signature/replay failures return 4xx with a structured error body; processing failures return 5xx so the sender may retry; nothing is partially applied |
| Rate limit | Per-source rate limit (recommended default 60/min, operator-tunable); overflow is rejected with `429` |

### Closed-schema validation

Each inbound `type` declares a JSON schema. Validation happens before any
effect (ADR-029's untrusted-input stance): a malformed or unknown payload
fails closed with `validation_error` and no side effect. C.1-C.3 map to
schemas as follows:

| Candidate | Inbound type | Payload schema (key fields) |
|---|---|---|
| C.1 push to main | `github.push` | `ref` == `refs/heads/main`; repository id; sender; head commit |
| C.2 issue/label change | `github.issue` | action (opened/edited/labeled/unlabeled/closed/reopened/transferred); issue number; label names; actor |
| C.3 review event | `github.pull_request_review` | action (submitted); PR number; review state; actor |

## Outbound events (Cortxt emits events to consumers)

### Envelope

Run/claim/label transitions publish one event each:

```json
{
  "id": "evt_01J1...",
  "type": "cortxt.workflow.transition",
  "occurred_at": "2026-08-23T12:00:00Z",
  "source": "cortxt",
  "data": {
    "issue_id": "owner/repo#123",
    "from": "workflow:ready",
    "to": "workflow:in-progress",
    "run_id": "run-abc123",
    "claim_id": "claim-xyz"
  }
}
```

- Emitted at every contractual `workflow:*` transition (ADR-018): ready ->
  in-progress -> review -> done, plus blocked.
- Content-free: no prompts, no model reasoning, no payloads — only
  identifiers and the transition, matching the dispatch-contract result
  envelope's content-free rule.

### Delivery and signing

- **Primary surface today: MCP** (ADR-024). The MCP server is the existing
  external integration form; outbound events are exposed as MCP
  notifications/tools rather than a new HTTP endpoint.
- **Optional webhook/event endpoint** for non-agent consumers (CI, status
  dashboards) is a small, non-redesign addition later (ADR-024 already
  allows a REST facade). When added, outbound events are HMAC-signed with
  a per-consumer secret and delivered at-least-once with a bounded retry
  schedule; consumers confirm with 2xx.
- Consumer registration is out of scope for v1 of this design (no public
  registry); consumers are operator-configured.

## Mapping the #305 candidates onto the surface

- C.1 (Pages auto-deploy): inbound `github.push` -> validate ref/main ->
  trigger the Pages deployment (or the operator-registered webhook
  already handles it; the surface standardizes the validation).
- C.2 (event-triggered Atlas sync): inbound `github.issue` -> validate
  action/label schema -> run `atlas_sync.py --emit-site --emit-graph`; the
  atlas bot's own writes emit no re-trigger (actor guard).
- C.3 (review-sync trigger): inbound `github.pull_request_review` ->
  validate -> run one `cortxt daemon sync-review` pass; the pass's own
  `workflow:review` label edit emits `cortxt.workflow.transition`
  (outbound) but is excluded from re-triggering inbound processing.

## Boundaries

- The surface never grants dispatch authority: graph position, frontier
  membership, or an inbound event alone never claims, labels, merges,
  approves, deploys, or closes anything (dispatch-contract).
- Inbound payloads are untrusted (ADR-029): closed-schema validated,
  signature-verified, replay-bounded, and never echoed into logs or
  GitHub.
- No secrets, prompts, or model reasoning cross the surface.
- This document proposes the surface; implementation is separate build
  issues with scope + AC + limits.

## Open questions (for the operator)

- Idempotency window and rate-limit defaults (recommended 5 min / 60 per
  min per source).
- Whether outbound events should also be subscribable by non-MCP
  consumers in v1, or strictly MCP-first per ADR-024.
- Whether the trust-marker enum in ADR-029 needs a third value (e.g.
  `untrusted_event`) once a generic inbound listener ships.
