# Atlas: roadmap maps on top of GitHub Issues

Status: active normative
Authority: repository governance
Last verified: 2026-08-22

Atlas is a map-based planning layer on top of the existing GitHub Issues
truth (ADR-018). It renders two levels of derived maps -- one global roadmap
map and one map per roadmap area -- from the durable issue record, and keeps
them fresh through automatic sync plus coordinator-driven updates. **Issues
remain the single source of truth; maps are derived views, never a second
backlog.**

Atlas replaces the earlier ad-hoc "wayfinder" convention
(`docs/agents/issue-tracker.md`'s former Wayfinding section). The name
"wayfinder" is deliberately not reused for Atlas -- it is a third-party skill
name.

## Map levels

- **Global map** -- one issue, `Area: Global`, label `atlas:map`. Covers all
  roadmap areas, the cross-area blocker chain, a milestone overview, and the
  current actionable frontier across the whole repository. Never archived.
- **Area map** -- one issue per roadmap area, `Area: <name>`, label
  `atlas:map`. Covers the issues wired to that area's milestone: status,
  relationships, milestone progress, decisions, and open questions.

## Map body structure (fixed)

Every map body has this exact shape. The metadata lines at the top and the
`## Destination` / `## Decisions so far` / `## Open questions` headings are
coordinator-owned; everything between `<!-- atlas:auto:start -->` and
`<!-- atlas:auto:end -->` is regenerated by `scripts/atlas_sync.py` and must
never be hand-edited (edits there are overwritten on the next sync).

```
Area: <Global | area name>
Milestone: <milestone title>        (area maps only)
Planning stage: <Exploring|Specified|Delivery|Reviewing|Complete>
Work kind: <decision|research|prototype|delivery|review|diagnosis>   (optional, per-issue convention; see below)

## Destination

<coordinator-owned prose>

<!-- atlas:auto:start -->
### Current state
### Execution path
### Blockers
### Actionable frontier
### Milestone progress            (area maps) / ### Milestone overview (global map)
### Relationship drift
### Discipline violations
### Review evidence
### Completion
### Last successful sync
<!-- atlas:auto:end -->

## Decisions so far

<coordinator-owned>

## Open questions

<coordinator-owned>
```

The `Area:` and `Milestone:` metadata lines are parsed by `scripts/
atlas_sync.py` (`Area:` selects global vs. area rendering; `Milestone:`
selects which issues belong to the area, by exact milestone-title match).
`Planning stage` and `Work kind` are read-only display conventions for
coordinators and are not parsed for sync logic beyond the `Work kind:` field
on individual work issues (see "Planning stage and work kind" below).

## Labels

- `atlas:map` -- identifies a map issue. **Not created by the sync script.**
  The coordinator creates this label once, out of band, before the first
  seed (see "Seed" below).
- `Area: <name>` -- one label per roadmap area, applied to the corresponding
  map issue (and optionally to its work issues) purely for GitHub's own
  filtering UI. Atlas sync does not require this label to function -- it
  reads the `Area:` body field, not a label -- but it is recommended for
  discoverability.
- `workflow:*` -- unrelated to Atlas itself; see ADR-018 and
  `docs/agents/issue-tracker.md`. Atlas reads and reports on these labels
  (one-label discipline, actionable frontier) but never writes them.

## Section ownership

| Section | Owner | Notes |
|---|---|---|
| Metadata (`Area:`, `Milestone:`, `Planning stage:`, `Work kind:`) | Coordinator | Read by sync for routing; never rewritten. |
| `## Destination` | Coordinator | Never touched by sync. |
| Everything between the `atlas:auto` markers | `scripts/atlas_sync.py` | Rewritten in full on every run that changes it; preserved byte-for-byte when there is nothing to rewrite. |
| `## Decisions so far` | Coordinator | Never touched by sync. |
| `## Open questions` | Coordinator | Never touched by sync. |

If a map body does not yet contain the `atlas:auto` markers, the sync
appends a new auto block at the end of the body on its first run rather than
failing.

## Relation contract

Atlas renders and validates issue relationships as a first-class feature,
using two edge kinds:

- **Containment** (parent/child): native GitHub sub-issue is canonical when
  available; the textual fallback is exactly `Part of: #<parent>` on its own
  line in the child's body. An issue has **at most one** immediate parent;
  more than one `Part of:` line (or a native parent that disagrees with the
  text) is reported as drift, never silently merged or picked.
- **Prerequisite** (blocks/blocked-by): the canonical phrase is
  `Blocked by: #<prereq>` on its own line, read from the blocked issue.
  `Depends on: #<prereq>` is accepted as a legacy read alias for the exact
  same directed edge (prerequisite -> blocked issue) -- it is never rewritten
  to the canonical form, just read as an equivalent input.

Reconciliation: when a native relation and a text relation describe the same
edge, the sync deduplicates them into one rendered edge. When they disagree
(different targets for a parent, for example), the sync renders **both**
sides as drift, with source attribution, and resolves nothing itself -- the
operator/coordinator decides.

Validation (drift, never silently corrected):
- target issue must exist;
- no self-edge (an issue cannot be its own parent or blocker);
- no dependency cycle (containment or prerequisite);
- no duplicate edge;
- at most one immediate `Part of` parent;
- native/text mismatch reported with both sides shown;
- cross-repo targets are rejected in v1 (Atlas is single-repo only);
- cross-area prerequisite edges are surfaced on the **global** map (cross-
  area blocker chain), not just the area map;
- missing area/milestone membership is reported, not guessed;
- **closed blockers are retained as completed history** -- they are shown on
  the map (tagged `[closed, history]`) but do not count against the
  actionable frontier.

All rendered references use `Title (#number)`, never a bare issue number.

## Actionable frontier

Each map renders an `Actionable frontier` subsection: open issues carrying
`workflow:ready`, exactly one `workflow:*` label, and every blocking
prerequisite closed or `workflow:done`. `workflow:in-progress` issues are
listed separately, as claimed current work, not as frontier candidates.

**Graph position on a map never grants dispatch authority.** The dispatch
contract (`docs/architecture/dispatch-contract.md`) remains the sole
authority for what may actually be claimed and run; Atlas only reports.

## Planning stage and work kind

- `Planning stage` (`Exploring` / `Specified` / `Delivery` / `Reviewing` /
  `Complete`) is a coordinator-owned field on the **map**, describing the
  area's own phase. It is not a second issue-state carrier -- ADR-018's
  `workflow:*` labels remain the only issue-state carrier.
- `Work kind` (`decision` / `research` / `prototype` / `delivery` /
  `review` / `diagnosis`) is an optional field in an individual **work
  issue's** body (`Work kind: <value>`), read by the sync and shown in
  `Current state` so decision/research/prototype/diagnosis work is visually
  distinguished from delivery/review work. Issues without the field default
  to `delivery` in the rendered output.

## One-workflow-label discipline

The sync enforces, as a read-only check, that every open work issue carries
exactly one `workflow:*` label. A violation (zero or multiple) is reported
under `Discipline violations` on every map that covers the issue -- it is
never auto-corrected.

## Review evidence

For issues carrying `workflow:review` or `workflow:done`, maps report the
presence or absence of two evidence kinds, read directly from the issue
body:
- `Contract fit: <note or link>` -- spec/acceptance-criteria verification;
- `Repository fit: <note or link>` -- rules/tests/governance verification.

Atlas renders presence/links only; it never generates a verdict. A missing
field renders as `MISSING`. A failed review creates or reopens a linked
diagnosis issue by coordinator action -- Atlas does not do this itself.

## Completion and archive

An area map is reported as `Complete: True` in its `Completion` subsection
only when both are true (checked automatically, nothing else):
- no open required work remains in the area (besides the map issue itself);
- every `workflow:review`/`workflow:done` issue in the area has both
  `Contract fit` and `Repository fit` evidence present.

This is a **report**, not an action: **Atlas never closes, reopens, or
archives an issue itself.** Archiving (and reopening) an area map is a
coordinator/operator action taken after reading the completion report. The
global map is never subject to archive; it is always preserved.

## Freshness and safe content

Every map's auto section ends with a `Last successful sync` timestamp. The
sync only rewrites a map when the regenerated content (ignoring that
timestamp) actually differs from what is already there, so re-running the
sync with no underlying changes is a no-op (no write, no comment). When a
map does change, the sync posts a concise summary comment on that issue.

If rendering a specific map fails, that failure is isolated: the map keeps
its last-good content (nothing is written), the failure is reported, and
every other map in the run still gets synced.

Before writing anything, the sync scans the generated content for a fixed
list of known-bad markers (credential-shaped strings, private-key headers,
prompt-leak markers). If any are found, the write for that map is skipped
and the run is reported as failed for that map -- generated bodies/comments
must never carry secrets, full prompts, private documents, raw sensitive
logs, or model reasoning.

## Native relations: best-effort

GitHub's native sub-issues/dependencies API is still rolling out. The real
`GhRunner` in `scripts/atlas_sync.py` attempts a best-effort native lookup
and degrades gracefully (native fields left empty) on any failure -- the
text conventions (`Part of:`, `Blocked by:`, `Depends on:`) remain a fully
supported path on their own, not merely a fallback for when native data is
temporarily unavailable.

## Projects relationship

Atlas is Projects-agnostic: it never requires a GitHub Project to be
configured, and it runs correctly with none configured. Per ADR-018, a
GitHub Project is used for workflow state only when the operator explicitly
designates one as current -- Atlas maps are a **complement**, never a
dependency: a future Project designation would be a board *view* over the
same issues Atlas already reads, never a second source of truth. The frozen
`Project 4` ("Legacy AI Workspace Delivery -- frozen") is excluded from
Atlas discovery entirely.

## Sync mechanics

- **Automatic:** `.github/workflows/atlas-sync.yml` ("Atlas sync") runs on
  `workflow_dispatch`, a daily `schedule`, and event triggers (issues,
  issue comments, merged pull requests), with `contents: read` and
  `issues: write` permission. It runs
  `scripts/atlas_sync.py --repo <owner/repo>`, which reads every
  open+closed issue via the injectable gh runner, regenerates each map's
  auto section, and posts a sync summary comment on each changed map --
  all of this uses the default `GITHUB_TOKEN`.
- **Publishing the derived site page/graph (PR-governed):** when the run
  changes `site/src/content/docs/docs/atlas-status.md` and/or
  `site/public/atlas/graph.json`, the workflow does **not** commit to
  `main` directly. It pushes a stable bot branch
  (`atlas-sync/bot-updates`) and opens or reuses a single pull request,
  using a short-lived **GitHub App installation token** minted from the
  `ATLAS_BOT_APP_ID` / `ATLAS_BOT_APP_PRIVATE_KEY` repository secrets (see
  "GitHub App requirements" below) -- never the default `GITHUB_TOKEN`,
  and never a plain `--force` push (only `--force-with-lease`, scoped to
  that one branch). If the App token is unavailable, the job fails with a
  clear error instead of silently falling back to `GITHUB_TOKEN`: a pull
  request authored/pushed with the default token does not trigger other
  workflows' `pull_request` events, so the publish PR's own CI would
  silently never run. Before committing, the workflow checks the changed
  paths against an allowlist of exactly those two files and refuses to
  commit if anything else changed. The workflow never merges, approves,
  or closes this pull request -- operator review and merge is required,
  same as any other pull request in this repository.
- **Coordinator-driven:** the coordinator updates the coordinator-owned
  sections (`Destination`, `Decisions so far`, `Open questions`, and the
  `Planning stage`/`Work kind` metadata) directly, and may trigger a manual
  `workflow_dispatch` run when a sync is needed sooner than the daily
  schedule.

### GitHub App requirements

The bot GitHub App used to mint the publish token needs exactly:

- **Repository permissions:** Contents (read and write), Pull requests
  (read and write).
- **No other permissions** -- in particular, no Issues permission: map
  issue reads/writes stay on the default `GITHUB_TOKEN`
  (`issues: write` in the workflow's `permissions:` block), so the App's
  own scope stays minimal.
- Installed only on this repository, with its App ID and a generated
  private key stored as the `ATLAS_BOT_APP_ID` /
  `ATLAS_BOT_APP_PRIVATE_KEY` repository secrets.

## Seed

Atlas maps are seeded by the coordinator after this feature merges -- the
sync script and its tests never create GitHub issues themselves. Seeding
uses the fixtures in `fixtures/atlas/` as the starting body:

```bash
# One-time: create the atlas:map label (coordinator action, not automated).
gh label create "atlas:map" --repo rian010194/cortxt \
  --description "Atlas roadmap map (auto-synced; see docs/agents/atlas.md)" \
  --color "0E8A16"

# Seed the global map.
gh issue create --repo rian010194/cortxt \
  --title "Atlas: Global roadmap map" \
  --label "atlas:map" \
  --body-file fixtures/atlas/global-map.md

# Seed the first area map, wired to milestone #3
# ("Open-source product packaging"), area "MCP lifecycle and dispatch stack".
# Edit fixtures/atlas/area-map-template.md's Area:/Milestone: lines first,
# or pipe a filled-in copy via --body-file.
gh issue create --repo rian010194/cortxt \
  --title "Atlas: MCP lifecycle and dispatch stack" \
  --label "atlas:map" \
  --milestone "Open-source product packaging" \
  --body-file fixtures/atlas/area-map-template.md
```

After seeding, run the "Atlas sync" workflow via `workflow_dispatch` (or
`python scripts/atlas_sync.py --repo rian010194/cortxt` locally with `gh`
authenticated) to populate the auto sections for the first time.
